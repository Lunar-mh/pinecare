# 银伴（SilverCompanion）前端设计与实现计划（可落盘版）

## 1) 概览

本计划用于在当前“仅有规格、无前端工程代码”的仓库基础上，完成银伴微信小程序前端（老人端+家属端）与社区管理端Web（模块013）的设计系统、页面/组件规范与工程化落地；全程以适老化与无障碍为硬约束（字号、对比度、热区、单屏信息架构、语音优先），并遵守微信小程序包体与后台限制，最终产出可构建、可验证、可迭代的完整前端代码与设计资产。

### 4.2 手工验收清单（每个迭代必须过）

适老化与无障碍：
- 字号：正文≥20sp、标题≥28sp、数据≥36sp（大字报表场景）
- 对比度：目标≥7:1；任何无法达到处必须说明并保证≥4.5:1
- 热区：所有可点控件≥44×44px；主操作≥60×60（pt/px等效）
- 单屏：单屏≤3个核心操作区；入口以“大图、大字、大按钮”呈现

语音：
- 唤醒词与入口：页面存在明显语音入口
- TTS语速：默认0.8倍；播放可打断；识别失败/权限拒绝有兜底

图表：
- 趋势图：`symbolSize: 12`、`lineWidth: 4`；坐标轴字体足够大且不拥挤
- Tooltip：可读性强（大字号、清晰单位），触控易命中

地图：
- 权限被拒：明确提示 + 可跳转设置；弱网：显示加载/错误态并可重试

弱网/离线：
- 关键接口失败：不崩溃；有明确错误态（大字）+ 重试按钮；避免“只靠颜色提示”

包体：
- 分包配置存在；主包资源最小化；引入资源时实时核验包体（实际大小：待工程产出后用构建报告核验）

## 5) 风险与未知项 + 缓解（末尾含开放问题与默认决策）

风险与缓解：
- 微信分包/包体限制（主包≤2MB/分包≤2MB/总≤20MB）：主包只放骨架与极少资源；图标SVG化；图片上CDN；按模块拆分分包并做资源审计。
- 字号缩放一致性（系统字体设置/关怀模式）：建立“字号映射表+极值换行策略”，避免布局崩坏；在页面规范中明确“文字不省略优先”。
- NutUI主题覆盖范围不足：对NutUI变量覆盖做清单；无法覆盖的组件用自研“适老组件”替代；所有交互热区以自研容器兜底。
- 语音能力与权限/失败兜底：录音权限、识别失败、TTS播放受限都必须有可见兜底；关键流程不依赖语音才能完成。
- ECharts性能与包体：采用按需引入（tree-shaking）与组件级封装；图表放入独立分包；低端机降级（减少动画/点数）。
- 无障碍审核项不一致/平台差异：以微信无障碍指南与工信部适老化规范为硬底线；任何例外要记录在页面规范与测试清单。
- 后台挂起（5秒）导致定位/音频/蓝牙中断：按产品文档策略“触发式定位、批量同步、订阅消息/短信兜底”；前端侧避免依赖后台常驻。

开放问题（不给你压力，提供默认决策）：
1) API端点总数是83还是93？
- 默认决策：以 `specs/*/contracts/openapi.yaml` 统计脚本为准，当前先按“约83~93（待核验）”写计划；差异只影响服务层文件数量与Mock覆盖范围。
2) 同声传译插件是否为最终语音方案？
- 默认决策：先按微信侧可用的语音能力实现UI与兜底；若后续替换ASR/TTS供应商，仅影响 `services/voice` 与权限/配置页面，不影响设计系统。
3) UI组件库最终选 NutUI 还是 Taro UI（或混用）？
- 默认决策：NutUI为主 + 自研适老组件兜底；若改为Taro UI，主要影响组件实现层，不影响tokens与页面布局原则。
