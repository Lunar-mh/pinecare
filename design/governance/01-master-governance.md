# 银伴四端协同开发总规

## 1. 文档定位

本文档是银伴后续四端协同开发的最高约束文件。后续任何 AI Agent、人工开发者、测试人员、答辩材料编写者，都必须先服从本文档，再开展具体设计与开发。

本项目在竞赛阶段的统一主轴为：

1. 竞赛优先
2. 证据优先
3. 闭环优先
4. 不夸大真实落地

## 2. 北极星目标

银伴不是单一小程序，而是一个面向社区居家养老场景的多角色协同照护平台。竞赛阶段的目标不是把 15 个模块平均做大，而是把最能体现项目价值的 5 条主链路做深、做稳、做可答辩。

五条主链路：

1. 链路 A：老人登录 -> 首页查看今日状态 -> 用药确认 -> 首页刷新
2. 链路 B：老人触发 SOS -> 家属收到风险感知 -> 社区后台进入处置中心 -> 事件流转关闭
3. 链路 C：家属查看长辈健康与定位 -> 家庭空间互动 -> 形成陪伴证据
4. 链路 D：社区后台创建或分派任务 -> 志愿者接单签到 -> 完成服务 -> 工时与时间银行状态更新
5. 链路 E：医疗资源查找 -> 在线咨询或预约 -> 报告同步 -> 家属与后台可见

## 3. 四端定义

### 3.1 老人端小程序

定位：低认知负担的日常照护入口。

### 3.2 家属端小程序

定位：远程守护与协同决策入口。

### 3.3 社区管理后台

定位：风险处置、运营协同、全局展示的指挥台。

### 3.4 志愿者端

定位：轻量任务执行端。

### 3.5 共享后端

定位：四端唯一业务中枢，不拆微服务。

## 4. 竞赛阶段的核心约束

1. 老人端与家属端继续共用一个 Taro 小程序代码库，不拆成两个前端项目。
2. 志愿者端保持轻量 H5 工作台路线，不重建为第二小程序。
3. 社区后台继续使用 Vue 3 技术栈，不扩写为重型企业中台。
4. 后端继续维持单体模块化 Express 架构，不引入微服务或消息中间件重构。
5. 新增功能必须满足以下条件之一：
   能增强核心演示闭环
   能补足真实落地短板
   能显著提高评审说服力
6. 不满足上述条件的新功能，不进入竞赛阶段路线。

## 5. 统一角色模型

固定角色枚举：

1. `elder`
2. `family`
3. `volunteer`
4. `community_admin`
5. `super_admin`

规则：

1. 小程序前台用户只允许 `elder` 与 `family`
2. 志愿者必须是独立身份，不复用社区管理员权限
3. 后台管理员必须区分社区范围与全局范围
4. 不允许后续 AI 随意新增角色

## 6. 开发优先级

### P0 必做

1. 老人端：首页、健康总览、今日用药、SOS、语音入口、家庭空间轻互动
2. 家属端：长辈状态、位置共享、SOS 查看、用药进度、家庭空间互动
3. 后台：工作台、用户管理、家庭绑定、健康监管、用药监管、SOS 风险中心、GPS 风险中心、社区看板
4. 志愿者端：今日任务、待接单、进行中、待确认、签到签退、SOS 协助、工时记录、培训提醒
5. 后端：角色鉴权、主链路接口、演示场景、审计、stub/live 模式稳定性

### P1 加分

1. AI 伴聊
2. 药物风险
3. 医疗资源入口
4. 时间银行贡献可视化
5. 志愿者成长与评级

## 7. 统一实施节奏

### V1 竞赛闭环版

完成链路 A、B、C 必达，链路 D、E 至少可演示。

### V1.1 答辩强化版

补后台证据展示、演示种子、录屏脚本、异常兜底话术。

### V1.5 冻结演示版

不再扩功能，只做联调、回归、自测和口径统一。

### V2 试点预备版

补志愿者真实任务流、真实社区规则、更多 live 接入。

## 8. 后续 AI 的执行规则

1. 每次开发前必须说明自己服务于哪条主链路。
2. 每次新增页面前必须说明其所属端、目标角色、依赖实体、调用接口和演示价值。
3. 每次新增状态或枚举前必须同步更新数据字典。
4. 每次新增接口前必须确认是面向前台“我的视角”，还是后台“全局视角”。
5. 每次开发结束后必须核对是否破坏总规与防跑偏清单。
