# 银伴·全域智慧照护平台 项目宪法

## 核心原则

### 一、数据真实性（NON-NEGOTIABLE）
数据使用必须为官方数据，严禁自主捏造。所有统计数据、文献引用、数据来源必须可追溯、可验证。涉及国计民生的核心数据（如老年人口数、健康数据等）应以国家统计局、卫健委、民政部等官方发布为准。

### 二、可落地优先
技术方案必须可实施，符合微信小程序平台限制。所有技术选型需考虑平台约束（如蓝牙后台断开、消息推送限制、定位策略等），优先选择已有成熟方案的路线，避免过度依赖理论可行但实际受限的技术。

### 三、中文优先
全程全部使用中文，没有用户允许不可使用英文，包括思考过程。英文仅保留必要的技术术语（如API、SDK等技术名称），文档标题、正文、注释一律中文。

### 四、删繁就简
技术栈精简，MVP优先，避免过度工程。后端采用轻量级方案（Node.js + Express + MySQL + Redis），前端使用Taro跨端框架，确保技术方案的可维护性与可实施性。非必要不引入额外技术组件。

### 五、前后一致性
文档与代码前后逻辑自洽，数据统一。文档中的所有数据（如人口数据、AI准确率、药物数据库条目数等）需在全文保持一致，版本发布前进行全文一致性检查。

### 六、分阶段交付
前端先完成完整形态UI设计，后端分三版迭代接入。第一版实现核心功能（健康数据同步、紧急呼叫、时间银行基础），第二版扩展AI能力与数据分析，第三版完善全场景覆盖与规模化优化。

### 七、适老化设计
面向老年人群体的无障碍、低学习成本设计。界面采用大字体、高对比度、简洁交互，核心操作步骤不超过3步，重要功能一步直达。考虑老年人数字素养差异，提供充分引导与容错设计。

## 技术约束与平台限制

### 微信小程序平台约束

**电话与消息限制**：紧急呼叫（SOS）需用户确认后方可拨打，无法实现自动拨打；消息订阅需用户主动授权，医疗类目可申请长期订阅，其他类目仅支持一次性模板消息。

**蓝牙连接限制**：BLE蓝牙后台连接会被系统断开，需采用"手环端批量采集 + 小程序端同步"模式，手环存储24小时内数据，用户打开小程序时触发一次性同步。

**定位策略限制**：小程序GPS定位需用户主动授权且需在前台运行，连续轨迹记录受限。解决方案：采用"主动触发 + 离开提醒"模式，用户需要时点击"查看位置"而非后台持续追踪。

**语音能力限制**：小程序无内置ASR（语音识别），需接入第三方服务（阿里云/讯飞）。考虑老年人普通话发音清晰度，优先支持主流方言识别。

### 技术栈边界

**后端MVP阶段**：Node.js + Express + MySQL + Redis + RabbitMQ，不引入Kafka、ClickHouse等技术，待规模化阶段再评估引入。

**前端阶段一**：Taro 3.x/4.x + Vue 3，先完成完整形态UI，暂不绑定具体后端API，待后端迭代完成后再对接。

**数据层**：药物相互作用数据库采用DDInter 2.0（中南大学湘雅，免费开源），不依赖商业数据库；时间银行采用数据库+数字签名+哈希链实现防篡改，MVP阶段不引入区块链。

### 数据合规要求

**个人信息保护**：严格遵守《个人信息保护法》，健康数据属于敏感个人信息，需单独授权，存储需加密，访问需审计。

**医疗器械合规**：智能健康设备需具备相应医疗器械注册证，药物提醒功能不替代医嘱，AI健康建议需明确标注为辅助参考。

## 开发工作流与质量门禁

### 代码审查要求

所有代码变更需经过至少一人Code Review，重点检查：技术约束合规性、数据一致性、适老化设计实现。

### 文档同步要求

产品文档更新时需同步检查：与其他关联文档的一致性、宪法原则的遵循情况、数据来源的时效性。

### 测试要求

功能测试覆盖所有用户交互路径，特别是适老化相关功能（字体大小、对比度、操作步骤）。性能测试关注首屏加载时间（目标3秒内）、接口响应时间（目标500ms内）。

### 发布门槛

功能发布前需满足：代码无阻塞性错误、文档更新完成、测试用例通过、宪法合规审查通过。

## 治理规则

### 宪法优先地位

本宪法为项目最高准则，优于其他开发规范与实践指南。任何技术决策、架构调整均不得违背宪法核心原则。

### 修订流程

宪法修订需经过以下流程：
1. 修订提案：说明修订原因、影响范围、实施方案
2. 评审：至少经过一轮核心团队评审
3. 批准：由项目负责人批准
4. 生效：修订版本发布后立即生效

### 版本策略

宪法版本采用语义化版本：MAJOR.MINOR.PATCH
- MAJOR：核心原则变更或重大约束调整
- MINOR：技术约束章节的补充完善
- PATCH：错别字修正、格式调整等微小变更

### 合规审查

所有项目里程碑发布前需进行宪法合规审查，确认：核心原则未被违背、技术约束得到遵守、开发工作流执行到位。

## 跨模块文件修改协议

当一次需求变更涉及**两个及以上模块**的文档或代码时，须遵守以下协议：

### 1. 变更范围声明

提交变更前，在 PR 描述或任务说明中列出所有受影响的模块及文件路径，格式：

```
跨模块变更范围：
- 模块 A (specs/00X-xxx/tasks.md) — 变更原因
- 模块 B (specs/00Y-yyy/plan.md)  — 变更原因
```

### 2. 原子性要求

同一次跨模块变更须在**同一 PR** 中完成，禁止拆分为独立 PR 分批合并，防止中间状态不一致。

### 3. 依赖声明同步

若模块 A 的 `plan.md` 新增了对模块 B 的依赖，则：
- 模块 A 的 `plan.md` → 更新 `Cross-Module Dependencies` 章节
- 模块 B 的 `plan.md` → 在 `Cross-Module Dependencies` 中注明被依赖关系

### 4. 接口契约变更

若变更涉及 API 路径、请求/响应字段修改，须同步更新：
- 发起方模块的 tasks.md（相关 T-task 描述）
- 依赖方模块的 plan.md `External Dependencies` 节

### 5. 数据库 Schema 变更

若变更导致共享表结构变化（如 `users`、`health_profiles`），须同步通知所有引用该表的模块维护者，并在迁移 SQL 文件注释中标注"跨模块影响：xxx 模块"。
